# Handoff — v0.2.1 (MMSC / KJS-FTB-MMSkillComponents)

Short delta on top of [v0.2.0.md](v0.2.0.md), which still holds the architecture,
the API contract and the gotchas. Read that one for the whole picture; this file
records what changed in 0.2.1, what the real cause of the dead settings panel was,
and what a successor must re-verify.

v0.2.1 is a bug-fix release: the DSH settings panel used to render its title and
then a single line, `无法读取工作台状态：HTTP 400 · (empty body)`, because **no host
route ever existed**. It now registers seven routes, and the test harness that let
two separate defects through has been tightened.

---

## 1. Symptom

DSH → Settings → 魔改工作台 rendered the title and one error line. Every
`/api/mmsc/*` call — including `ping`, which touches neither config nor the child
process — returned **HTTP 400 with an empty body**.

An empty 400 is the signature of DSH's shared `/api` RPC interceptor: when no exact
Fetch route matches a path, the request falls through to the RPC parser, which
rejects it before any handler runs. It therefore means "no route", not "handler
threw".

The page itself is served from `dsh-app://app/` (an Electron custom protocol), not
from `http://127.0.0.1:<port>`. `new URL('api/mmsc', document.baseURI).pathname`
still yields `/api/mmsc`, and the protocol handler forwards `/api/*` to the host, so
the URL shape was never the problem.

## 2. Root cause (two defects, both fatal on their own)

### 2a. `ctx.inject` wrapped in `ctx.effect` (fixed first, did not resolve it alone)

```js
ctx.effect(
  () => ctx.inject(['connection'], (scope) => { /* routes */ }),
  'mmsc-workbench: routes',
);
```

A Cordis effect factory must **return a disposer**; `ctx.inject(...)` returns
`undefined`, so the effect throws and the whole row aborts. Fixed by calling
`ctx.inject(['connection'], cb)` directly at `apply()` level, exactly like
`dsh-model-visibility/index.js:197`, and wrapping only the individual
registrations:

```js
ctx.inject(['connection'], (scope) => {
  const register = (route) =>
    scope.effect(() => scope.connection.fetch.register(route), `mmsc-workbench: ${route.path}`);
  register({ path: `${API}/ping`, methods: ['GET'], requestBody: 'buffered', fetch: … });
});
```

### 2b. GET routes omitted `requestBody` (the defect that still blocked everything)

`ConnectionFetchRoute` is `{ path, methods, requestBody: 'buffered'|'streaming', fetch }`.
`requestBody` is part of the contract for **every** method, including `GET`; the
known-good route in `dsh-model-visibility/index.js:279` sets it on a GET too.

Our `ping` and `status` routes left it out. `register()` rejects such a route, the
rejection happens inside the row's `apply()`, and the row aborts — again with no
route and no error surface visible to the renderer. Both GET routes now carry
`requestBody: 'buffered'`.

### 2c. Why the row's failures were invisible

A throw inside `apply()` is not reported to the browser: the settings page can only
observe the empty 400. `index.js` now appends a line to **`$DSH_HOME/mmsc-load.log`**
(`module` load, `apply:enter`, one line per route, `apply:ok`, or `apply:threw` with
a stack). If that file stays empty after a restart, the row was never imported at
all — a bundle/loader problem, not a plugin bug. Never put this kind of probe in the
renderer; it cannot see host-side failures.

## 3. Why the tests did not catch it

The fake context accepted anything:

```js
effect(factory) {
  const dispose = factory();
  if (typeof dispose === 'function') disposers.push(dispose);   // undefined tolerated
  return dispose;
}
```

It now mirrors Cordis **and** the route contract:

```js
effect(factory) {
  const dispose = factory();
  if (typeof dispose !== 'function') throw new TypeError('effect factory must return a disposer');
  disposers.push(dispose);
  return dispose;
}

register(route) {
  if (route.requestBody !== 'buffered' && route.requestBody !== 'streaming')
    throw new TypeError(`route ${route.path} is missing requestBody`);
  if (!route.path.startsWith('/api/')) throw new TypeError(`route ${route.path} must live under /api`);
  routes.set(route.path, route);
  return () => routes.delete(route.path);
}
```

Plus a route-inventory test asserting all seven routes (`ping`, `status`, `config`,
`start`, `stop`, `restart`, `open`). Baseline is **57/57** (`node --test` from the
repo root).

## 4. Panel behaviour when the host half is missing

The panel no longer collapses into one error line. It renders the whole form from
defaults (`port 5599`, empty pack dir, auto-open on) and:

- shows a status pill `面板未接通` plus the host error and a one-line explanation;
- **probes the workbench port directly** from the browser
  (`http://127.0.0.1:<port>/api/v1/version`, 1.5 s timeout) and reports
  「工作台端口 N 可访问 / 未响应」 — this works without the host half, because the
  workbench sends CORS headers;
- keeps 打开可用 (it falls back to `window.open` on the raw port);
- disables 保存 / 启动 / 重启 / 停止 with an explicit reason instead of hiding them.

The first refresh also pings and prints the resolved API base
(`document.baseURI → /api/mmsc`), so a future failure states where it looked.

## 5. Verify after restarting DSH

1. Quit the desktop app completely, start it again (a renderer reload is not
   enough — bundle host rows mount during startup).
2. `$DSH_HOME/mmsc-load.log` must contain `module`, `apply:enter`, seven `route …`
   lines and `apply:ok`. If it is missing or has `apply:threw`, read the stack —
   that is the actual error, and it is not visible anywhere else.
3. Settings (`Ctrl+,`) → 魔改工作台: 「主机路由已连通（/api/mmsc/ping · pid …）」,
   pill `stopped`, port field `5599`.
4. 启动 fills the URL, 在浏览器打开 opens the workbench, 重启 keeps the port and swaps
   the pid, 停止 releases it, 保存 persists to `$DSH_HOME/mmsc-workbench.json`.

## 7. Still open

  are complete and `origin` is configured.
- GUI verification (section 5) must be done by a human on the desktop session; it
  cannot be automated from inside the app that hosts it.
- Cosmetic debt: recipes produced by mod logic are labelled as such instead of
  showing a fake result; a version-less `kubejs.jar` is detected as
  `generation assumed (newest)` rather than guessing a number.
