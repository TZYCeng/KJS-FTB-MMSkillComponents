# KubeJS + FTB Quests modpack work

Two systems, four API generations, one rule: **never write gameplay code before you know the exact Minecraft / mod version of the pack.** KubeJS changed its whole scripting surface twice (1.19 and 1.21), and FTB Quests moved quest text out of the chapter file in 1.21. Code that looks right in a tutorial is the most common way to ship a pack that silently does nothing.

## The five facts that decide everything

1. **`onEvent(...)` is dead from 1.19 on.** 1.16.5 / 1.18.2 use `onEvent('recipes', event => {})`; 1.19.2 / 1.20.x / 1.20.4 use `ServerEvents.recipes(...)` (calling `onEvent` there binds a stub that **throws** at runtime); 1.21+ has no `onEvent` binding at all (`ReferenceError`).
2. **FTB Quests data is SNBT, not JSON**, from 1.16 onward: `config/ftbquests/quests/{data.snbt, chapter_groups.snbt, chapters/<name>.snbt, reward_tables/<name>.snbt, lang/<locale>.snbt}`.
3. **The `version: 13` field in `data.snbt` does not identify the pack version** — every FTB Quests release since 1.16 writes 13. Use the jar version.
4. **From 1.21 (FTB Quests 2101) quest and chapter text lives in `lang/<locale>.snbt`**, keyed `quest.<16-hex-id>.title` / `.quest_desc` / `.quest_subtitle` and `chapter.<id>.title` / `.chapter_subtitle`. A 1.21 quest compound has no `title` field; writing one is silently ignored.
5. **Ids are 16 uppercase hex digits** generated by FTB Quests, unique across the whole quest file. Never copy an id from another chapter, and never reuse the chapter id as a quest id — the validator reports that as `dependency-dangling`.

## Step 0 — always detect first

```bash
node bin/kjsftb.mjs detect <pack-dir>
```

Run this from this skill's directory (`node <this-skill-dir>/bin/kjsftb.mjs ...`). It reads `modrinth.index.json`, CurseForge `manifest.json`, `minecraftinstance.json`, Prism `mmc-pack.json`, the KubeJS jar name, or the quest directory, and prints the Minecraft version, loader, KubeJS generation, FTB Quests generation, script folders and quest file inventory.

If the pack directory is not available, ask for it (or for the mod list); do not guess between 1.20.1 and 1.21.1 — the two produce incompatible code.

Version → generation → reference to load:

| Minecraft | KubeJS build prefix | generation | script syntax | reference |
|---|---|---|---|---|
| 1.16.5 | 1605 | `legacy` | `onEvent('recipes', ...)` | `references/kubejs-legacy.md` |
| 1.18.2 | 1802 | `legacy` | `onEvent('recipes', ...)` | `references/kubejs-legacy.md` |

## KubeJS workflow

1. Write the script into `kubejs/server_scripts/` (recipes, tags, loot, most player/level events) or `kubejs/startup_scripts/` (registry entries, `StartupEvents`, block/item modification). Client-only events belong in `client_scripts/`. Guessing the folder wrong is a silent no-op — the linter flags it as `stage-mismatch`.
2. Prefer generating the skeleton, then edit:
   ```bash
   node bin/kjsftb.mjs recipe new --spec recipe.json --out kubejs/server_scripts/my_recipes.js
   ```
   `recipe.json` is `{ "priority": 10, "version": "2101.7.2", "recipes": [ ... ] }`; supported `kind`s are listed in `references/recipes.md` and in `RECIPE_KINDS`. Copy-ready specs live in `templates/recipe-basic.json` and `templates/recipe-edits.json`. When no pack is visible, `--generation 1.20.1` doubles as a version hint (the schema-dependent smithing forms follow it), and the generator never emits a helper the target generation lacks — unsupported calls become `// skipped:` comments.
3. Remove or replace recipes with filters, not by editing mod files: `event.remove({ output: 'mod:item' })`, `event.replaceInput({ id: 'minecraft:torch' }, 'minecraft:stick', 'mod:rod')`, `event.replaceOutput(...)`. Filter grammar (string, regex, `*`/`-` prefixes, arrays, `output`/`input`/`mod`/`id`/`type`/`not`) is in `references/recipes.md`.
4. Validate: `node bin/kjsftb.mjs lint <pack-dir>` — it knows the generation, so it rejects `onEvent` on 1.21, `ServerEvents` on 1.16, members that moved between versions (`ItemEvents.tooltip` → `modifyTooltips`, `EntityEvents.hurt` → `beforeHurt`/`afterHurt`, `REIEvents` → `RecipeViewerEvents`), legacy ids that belong to the other legacy branch, recipe calls that would wipe every recipe (`legacy-destroy-all-filter`), wrong `smithing`/`smithing_trim` arity, and scripts in the wrong folder. Fix every error before continuing; `--strict` also fails warnings.

## FTB Quests workflow

1. Read `references/ftbquests-format.md` for the file layout, key maps, id rules and lang mechanics.
2. Prefer generating/editing through the CLI so ids and lang keys stay consistent:
   ```bash
   node bin/kjsftb.mjs quest new <pack-dir> --spec quest.json --write
   node bin/kjsftb.mjs quest chapter <pack-dir> --spec chapter.json --write
   node bin/kjsftb.mjs quest id            # fresh unique 16-hex id
   ```
   A quest spec carries `chapter` (filename), `title`, `subtitle`, `description` (array of lines), `icon`, `shape`, `size`, `x`/`y` (optional; auto-placed below the last quest), `tasks`, `rewards`, `dependencies`, and flags such as `optional` / `invisible` / `canRepeat` (camelCase for the longer flags: `minRequiredDependencies`, `hideLockIcon`, `repeatCooldown`, `invisibleUntilTasks`). On 1.21+ the generator writes the text into `lang/en_us.snbt` instead of the chapter. Copy-ready specs: `templates/quest.json` and `templates/chapter.json`.
3. Validate after every edit: `node bin/kjsftb.mjs ftbq <pack-dir>` (add `--ftbq 1.20.1` when the pack's FTB Quests build is unknown). It checks ids, dangling dependencies and reward-table references, unknown task/reward types, missing required fields, fields that the target version would silently drop (`field-too-new`), lang key shapes, orphan translations, duplicate ids, overlapping quests, and chapter filename mismatches.
4. Editing by hand is fine for small changes, but keep FTB's layout: tab indentation, one entry per line, `0.0d` for doubles, and ids as the compound keys. `snbt format` / `snbt check` handle the formatting and syntax side.

## Task and reward types are version-gated

The full table is in `references/ftbquests-types.md`. Highlights: `interaction` tasks and `currency` rewards exist only in 1.21.1+; `all_table` rewards only from 1.20.1; `xp_levels` exists in every version; `fluid` and `forge_energy` tasks are registered per loader (Fabric packs lack `forge_energy`). A type the target version does not register is **not** dropped with an error — the loader substitutes a Custom task/reward titled `Unknown type: <id>` that never completes and saves back as `type: "custom"`, losing the original spelling. A missing `type` defaults to an item task, which completes on the first item pickup. That is why the validator flags both instead of trusting the file.

## Rules that prevent most rework

- **Legacy filters must be maps.** On 1.16.5/1.18.2 `event.remove('minecraft:torch')` is not "remove that recipe": `RecipeFilter.of()` returns match-everything for a string or a list containing one, so it deletes **every recipe in the pack** (same for `replaceInput`/`replaceOutput`, and for `*`/`-`, which are ingredient strings there). Write `event.remove({ output: 'minecraft:torch' })`. From 1.19 on, strings are recipe-id/output filters and are safe — the linter separates the two as `legacy-destroy-all-filter`.
- **Legacy ids differ per branch.** 1.16.5 uses `world.*`, `entity.attack`, `block.drops`, `block.tags`, `item.tags`, `fluid.tags`, `entity_type.tags`, `client.paint_world`; 1.18.2 renamed those to `level.*`/`entity.hurt` and dropped the tag/drop ids, adding `item.model_properties` and `client.generate_assets`. There is no `player.decorate_chat` and no `network.data_received` in either branch — networking is `player.data_from_server` / `player.data_from_client`.
- **An unknown event id never throws.** `PlayerEvents.respawnned(...)` logs one line — `Unknown event 'PlayerEvents.respawnned'!` — and returns a no-op function, so the handler silently never runs. The linter knows the real id list for the detected generation; trust it over memory.
- **Events have a side.** `ServerEvents`, `PlayerEvents`, `LevelEvents`, `EntityEvents` and `NetworkEvents` are common-gated: putting one in `startup_scripts/` throws `Tried to register event handler ... for invalid script type`. Registry work (`StartupEvents.registry`, `ItemEvents.modification`, `BlockEvents.modification`) must be in `startup_scripts/`, client-only events in `client_scripts/` (`stage-mismatch`).
- **`event.shaped` is not vanilla JSON.** It creates a `kubejs:shaped` recipe (accepts `Item`/`Ingredient` and KubeJS item properties); use `event.vanillaShaped` or `event.custom({ type: 'minecraft:crafting_shaped', ... })` when the exact vanilla serializer matters.
- **Do not mix generations in one pack.** A pack has exactly one KubeJS generation; scripts written for another generation either throw or do nothing. When porting a pack, rewrite the event wrappers, not just the recipe bodies.
- **Recipe schema arg order is not guessable.** `smithing` is result-first everywhere; 1.19.2 takes exactly `(result, base, addition)`, 1.20.1/1.21 accept both 3-arg and `(result, template, base, addition)`, `smithingTrim` is `(template, base, addition)`. Check `references/recipes.md` before writing smithing code.
- **`priority` header**: `// priority: N` in a script, higher runs first (the default is 0); a non-integer value (`// priority: high`) makes KubeJS log "Failed to pre-load script file" and skip the file entirely. Ties are not portable: on 1.16–1.20.1 `ScriptFile.compareTo` compares only the priority, so equal scripts keep the mod's file-discovery order; on 1.21.1 / 26.1.2 (`ScriptFile.java:117` / `:127`) the tie-break is `locationPath.compareToIgnoreCase` — alphabetical by path. Never rely on either for ordering between files: set explicit priorities.
- **Text encoding**: write files as UTF-8 **without BOM**, and do not round-trip them through PowerShell `Get-Content -Raw` / `Set-Content` (it corrupts non-ASCII characters). Use the editor tools, or `[System.IO.File]::ReadAllText/WriteAllText` with `UTF8Encoding($false)`.
- **Never edit `mods/*.jar` or mod source.** FTB Quests is source-visible but not licensed for redistribution; KubeJS is LGPL-3.0. Pack-side work is data and scripts only.
- **Back up before rewriting**: `data.snbt`, `chapter_groups.snbt`, and chapter files are the whole pack's progression. Copy the `quests` folder before a bulk edit, and diff after.
- **A quest with no tasks is a real, common bug** (`quest-no-tasks`); use a `checkmark` task for pure gating or lore quests.

## CLI summary

| command | purpose |
|---|---|
| `detect [dir]` | versions, loader, script folders, quest inventory |
| `lint [dir] [--strict]` | KubeJS scripts against the detected generation |
| `ftbq [dir] [--ftbq <ver>] [--no-info]` | validate quest SNBT data |
| `snbt check <file\|dir>` | parse SNBT, report line/column errors |
| `snbt format <file> [--write]` | re-emit in FTB layout |
| `recipe new --spec <json> [--out <file>]` | generate recipe script |
| `quest new / quest chapter / quest id` | generate quest data, ids |
| `--json` on any read command | machine-readable output |

Exit codes: `0` clean, `1` problems found, `2` usage error.

## Reporting back

When you finish a change, state: the detected versions, the files written, the validator/lint result (error/warning counts, not just "OK"), and what the pack owner must verify in-game. Reloading is version-specific: 1.16.5/1.18.2 need a world reload for script changes and `/reload` only reloads datapack recipes; 1.19.2/1.20.1 reload scripts with `/reload` (or `/kubejs reload server_scripts`); 1.21+ uses `/kubejs reload server_scripts` and F3+T for client assets. Check the generation reference before promising a command.
